# Промт для генерации тест-кейсов AllerGuide

Этот документ содержит готовый промт, который можно передать LLM (ChatGPT,
Claude, Cursor и т.п.) или QA-инженеру для генерации тест-кейсов по
функциональности мобильного приложения **AllerGuide**.

Промт построен на основе [`docs/functional-requirements.md`](./functional-requirements.md)
(ТЗ v13) и охватывает все экраны, FR-идентификаторы и интеграции, описанные
в спецификации.

---

## 1. Как пользоваться

1. Скопируйте раздел [«Промт»](#2-промт-копировать-целиком) целиком.
2. Подставьте значения в блок `<<ВХОДНЫЕ ДАННЫЕ>>`:
   - `<<МОДУЛЬ>>` — конкретный раздел (например, «Дневник», «Сканер»,
     «SOS», «Профили», «Главная», «Карта», «Маркет», «Эксперт», «Настройки»,
     «Аутентификация», «Онбординг») **или** `ALL` для всего приложения.
   - `<<ПЛАТФОРМА>>` — `iOS`, `Android`, `Web` или `ALL`.
   - `<<ТИПЫ_ТЕСТОВ>>` — список через запятую из:
     `positive, negative, edge, boundary, ux, a11y, perf, security, offline, i18n, regression`.
     Можно указать `ALL`.
   - `<<ПРИОРИТЕТ>>` — `P0, P1, P2` или `ALL`.
   - `<<ФОРМАТ_ВЫВОДА>>` — `markdown-table`, `gherkin`, `json`, `xray-csv`
     или `testrail-csv`.
   - `<<ЯЗЫК>>` — `ru` (по умолчанию) или `en`.
3. При необходимости приложите к запросу содержимое
   `docs/functional-requirements.md` как контекст.
4. Отправьте промт модели и получите тест-кейсы в указанном формате.

## 2. Промт (копировать целиком)

```
Ты — старший QA-инженер с опытом тестирования мобильных приложений на
Expo / React Native (iOS, Android, Web). Твоя задача — спроектировать
исчерпывающий набор тест-кейсов для приложения AllerGuide.

# Контекст продукта

AllerGuide — offline-first мобильное приложение-помощник для людей с
аллергией и их родителей. Русскоязычный UI (поддержка 6 языков),
6 нижних вкладок: Главная, Дневник, Сканер, Маркет, Карта, SOS.
Хранение: SQLite на native, localStorage на web. Опциональный backend
(Express + PostgreSQL) для auth и sync. Внешние интеграции:
Open-Meteo (пыльца / EAQI / PM2.5), Open Food Facts (штрихкоды),
Expo Camera / Location / Print / Notifications.

Полный перечень функциональных требований с идентификаторами
FR-* приведён в файле docs/functional-requirements.md (версия 1.0,
основание — ТЗ v13). Считай его источником истины и опирайся на
конкретные FR-ID при формировании тест-кейсов.

Ключевые ограничения, которые нужно учитывать в тестах:
- Web-режим: нет камеры штрихкодов, нет push, localStorage вместо SQLite.
- Приложение НЕ ставит диагноз — на всех медицинских экранах обязателен
  disclaimer.
- Раздел «Пикфлоуметрия» виден только при наличии астмы в профиле.
- Раздел «АСИТ» виден только при поллинозе/рините/бытовой/животной аллергии.
- Активный профиль переключается на основных экранах; повторный тап по
  активному профилю открывает редактирование.
- Удаление профиля каскадно удаляет связанные записи дневника и историю.
- Скан учитывает перекрёстные реакции из справочника аллергенов.
- Wellness index 0–100 зависит от данных Open-Meteo + дневника за 48 ч.
- PDF-отчёт: периоды 7/14/30 дней, набор блоков выбирается пользователем.
- SOS-номер настраивается, по умолчанию 103.
- Резервная копия — JSON v1 с timestamp.

# Что нужно сделать

1. Определи все пользовательские сценарии и состояния указанного модуля
   на основе соответствующих FR-* из docs/functional-requirements.md.
   Если модуль = ALL — пройди по всем разделам спецификации (главы 4–14).
2. Для каждого сценария сгенерируй тест-кейсы выбранных типов:
   - positive   — основной happy path.
   - negative   — некорректный ввод, ошибки API, отказ в разрешениях.
   - edge       — пустые/максимальные значения, спецсимволы, эмодзи,
                  длинные строки, юникод, RTL, переполнение, 0 элементов.
   - boundary   — границы валидации (телефон 9/10/15/16 цифр, пароль
                  5/6/7 символов, шкала симптомов −1/0/10/11 и т.п.).
   - ux         — навигация, состояния загрузки, пустые состояния,
                  обратимость, подтверждения удаления, disclaimers.
   - a11y       — контраст, размер touch-target (≥44pt), screen reader,
                  динамический размер шрифта.
   - perf       — холодный старт, отзывчивость списков (≥100 записей),
                  PDF-генерация, скан штрихкода.
   - security   — авторизация, изоляция данных между профилями,
                  чувствительные данные в логах/бэкапе, deep links.
   - offline    — поведение без сети (Open-Meteo, Open Food Facts,
                  sync API), переход online→offline в процессе.
   - i18n       — переключение языка (ru/en/es/fr/de/it), сохранение
                  выбора, форматирование дат/чисел, длинные переводы.
   - regression — критические пути, которые нельзя ломать (bootstrap,
                  CRUD профилей, дневник, SOS-звонок).
3. Учитывай матрицу платформ: помечай кейсы, применимые только к
   native, только к web, или ко всем. Web-only ограничения проверяй
   отдельными кейсами (камера недоступна, push недоступны и т.п.).
4. Для каждого тест-кейса укажи:
   - ID:                 TC-<МОДУЛЬ>-<NNN> (например, TC-DIARY-001)
   - Название:           краткое, в формате «Действие → ожидаемый результат»
   - Связанные FR:       список FR-ID из спецификации
   - Приоритет:          P0 (блокер) / P1 (важно) / P2 (полезно)
   - Тип:                positive | negative | edge | boundary | ux |
                         a11y | perf | security | offline | i18n | regression
   - Платформа:          iOS | Android | Web | ALL
   - Предусловия:        состояние приложения, профиля, данных, сети,
                         разрешений (камера, геолокация, уведомления)
   - Тестовые данные:    конкретные значения (имя, телефон, аллергены,
                         штрихкоды, симптомы по шкале и т.п.)
   - Шаги:               пронумерованный список (1, 2, 3 ...) —
                         каждое действие пользователя одной строкой
   - Ожидаемый результат: что именно должно произойти на каждом важном
                         шаге, включая UI-состояние, данные в БД, отчёт
                         disclaimer, аналитику
   - Postcondition:      состояние данных/экрана после теста (опционально)
   - Заметки:            edge-conditions, известные ограничения,
                         ссылки на «Планируется» из ТЗ

5. Сгруппируй тест-кейсы по экранам/маршрутам из раздела 19
   спецификации («Матрица экранов»).
6. В конце сделай матрицу покрытия: таблица «FR-ID → список TC-ID»,
   чтобы видеть, что каждый FR покрыт хотя бы одним кейсом. Явно
   отметь FR, для которых сгенерировать тест невозможно (например,
   OUT-* — запланированные, не реализованные функции) и поясни почему.

# Правила оформления

- Все шаги формулируй в повелительном наклонении: «Открой», «Нажми»,
  «Введи». Один шаг = одно действие.
- Не используй размытые ожидания вроде «всё работает». Указывай
  конкретный UI-элемент, текст, статус, поле БД.
- Для негативных тест-кейсов всегда указывай конкретное сообщение
  об ошибке (текст или ID строки локализации, если известен).
- Учитывай два режима хранения (SQLite native / localStorage web)
  при проверках персистентности.
- Для интеграций с внешними API (Open-Meteo, Open Food Facts, sync)
  предусмотри кейсы: успех, 4xx, 5xx, таймаут, отсутствие сети,
  невалидный ответ.
- Тест-кейсы по медицинским экранам обязательно проверяют наличие
  disclaimer (главный экран, дневник, сканер, эксперт, SOS, отчёт).
- Для SOS обязательны кейсы: пустой профиль, профиль без контактов,
  ребёнок без телефона, отказ в разрешении на звонок,
  переопределённый номер экстренной службы.

# Формат вывода

Сначала кратко (3–5 строк) опиши, как ты интерпретировал входные
данные и сколько кейсов будет сгенерировано. Затем выведи тест-кейсы
строго в формате <<ФОРМАТ_ВЫВОДА>>:

- markdown-table — одна таблица со столбцами:
    ID | Название | FR | Приоритет | Тип | Платформа | Предусловия |
    Данные | Шаги | Ожидаемый результат | Заметки
  Многострочные ячейки — через `<br>`.
- gherkin — каждый кейс как сценарий:
    Feature: <модуль>
    Scenario: <ID> — <название>
      Given <предусловие>
      And <данные>
      When <шаг>
      Then <ожидание>
  Метаданные (FR, приоритет, платформа, тип) — в виде @tag над сценарием.
- json — массив объектов с полями, перечисленными в пункте 4. Без
  комментариев, валидный JSON.
- xray-csv / testrail-csv — CSV с заголовком первой строкой,
  разделитель «;», экранирование двойных кавычек по RFC 4180.

В конце вывода всегда добавляй раздел «Coverage matrix» с таблицей
FR-ID → TC-ID, даже если основной формат — JSON или CSV
(её приведи отдельным markdown-блоком).

# Чек самопроверки (выполни перед выводом)

- [ ] Каждый выбранный FR из спецификации имеет ≥1 связанный тест-кейс
      ИЛИ явно отмечен как непокрываемый с обоснованием.
- [ ] Покрыты все запрошенные типы тестов из <<ТИПЫ_ТЕСТОВ>>.
- [ ] Для web/native различий есть отдельные кейсы.
- [ ] У всех тест-кейсов уникальные TC-ID.
- [ ] Шаги однозначно воспроизводимы (нет «и т.д.», «и так далее»).
- [ ] Использован только указанный язык (<<ЯЗЫК>>).
- [ ] Соблюдён указанный формат вывода (<<ФОРМАТ_ВЫВОДА>>).
```

## 4. Рекомендации по применению

- Для длинных модулей (например, `Дневник`) запускай промт отдельно
  по типам тестов, иначе модель может обрезать вывод.
- Перед отправкой больших партий генераций приложи к контексту
  актуальную версию `docs/functional-requirements.md` — это снизит
  количество галлюцинаций по FR-ID.
- Полученные тест-кейсы перед импортом в TestRail / Xray проверяй
  по «Coverage matrix»: пустые ячейки = пробелы в покрытии.
- При расширении спецификации обновляй раздел «Контекст продукта» в
  промте, чтобы модель видела новые ограничения и фичи.
