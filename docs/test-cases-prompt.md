# Промт для генерации тест-кейсов AllerGuide

Готовый промт для LLM (ChatGPT, Claude и т.п.), который генерирует тест-кейсы
функциональности приложения **AllerGuide**. Скопируйте блок «Промт» целиком,
при необходимости подставьте значения в плейсхолдеры `{{...}}` и отправьте модели.

- **Источник истины по функциям:** `docs/functional-requirements.md` (идентификаторы FR-*).
- **Назначение:** подготовка ручных и регрессионных тест-кейсов для QA и приёмки.
- **Язык результата:** русский.

---

## Как пользоваться

1. Определите область тестирования и заполните плейсхолдеры:
   - `{{SCOPE}}` — что покрываем (например: «весь дневник», «сканер, режим Продукт», «весь App»).
   - `{{PLATFORM}}` — `iOS`, `Android`, `Web (Expo)` или `все платформы`.
   - `{{FR_IDS}}` — конкретные требования (например `FR-DIARY-01…07`) или `все релевантные`.
   - `{{DEPTH}}` — `smoke`, `основные сценарии` или `полное покрытие с негативными и граничными`.
   - `{{FORMAT}}` — `Markdown-таблица`, `Gherkin (Given/When/Then)` или `JSON`.
2. (Опционально) приложите к запросу содержимое `docs/functional-requirements.md`,
   чтобы модель опиралась на точные FR-идентификаторы.
3. Отправьте промт модели и проверьте, что каждый тест-кейс ссылается на FR.

---

## Промт

````text
Ты — старший QA-инженер, готовящий тест-кейсы для мобильного приложения AllerGuide.

# Контекст продукта
AllerGuide — кроссплатформенное приложение (Expo / React Native: iOS, Android, Web)
для управления аллергией с русскоязычным интерфейсом. Приложение offline-first:
на native данные хранятся в SQLite, на web — в localStorage с тем же API.
Приложение НЕ ставит диагноз и не заменяет врача — на всех медицинских экранах
обязателен disclaimer.

Ключевые функциональные блоки:
- Аутентификация: регистрация/вход по телефону или email + пароль; выход; удаление аккаунта.
- Bootstrap и онбординг: intro (5 слайдов) → выбор сценария (я / ребёнок / я и ребёнок)
  → создание профиля(ей); согласие родителя для детского профиля.
- Профили: CRUD, выбор аллергенов из каталога (10 типов аллергических состояний),
  перекрёстные реакции, экстренные контакты, переключение активного профиля,
  каскадное удаление; условные модули дневника (Пикфлоуметрия — при астме, АСИТ — при
  поллинозе/рините/бытовой/животной аллергии).
- Главный экран: wellness index 0–100 (пыльца, качество воздуха, записи дневника),
  факторы, рекомендации, быстрые ссылки, переход в SOS.
- Дневник: разделы Симптомы, Лекарство, Питание, Триггер, Кожа, Пикфлоуметрия, АСИТ,
  Визит к врачу, Заметка; пошаговый wizard, быстрые записи, редактирование, удаление,
  история, summary; PDF-отчёт для врача (период 7/14/30 дней, выбор блоков).
- Сканер: режимы Продукт / Меню / Лекарство / Косметика; штрихкод (Open Food Facts),
  ручной ввод состава, демо-анализ меню; вердикт с уровнем риска (низкий/средний/высокий),
  совпадения, перекрёстные совпадения, источник, история (до 5 записей).
- Маркет: каталог товаров, персональная фильтрация по аллергенам профиля, поиск.
- Карта: слои Рестораны (геолокация, уровни безопасности, на web — заглушка), Пыление
  (сезонный календарь), АДАИР (клиники и врачи).
- Эксперт: категории и статьи справочного контента.
- SOS: имя/возраст/аллергены, медицинские заметки, план действий, экстренные контакты,
  звонок одним нажатием, настраиваемый экстренный номер (по умолчанию 103).
- Настройки: экстренный номер, тема (светлая/тёмная/системная), напоминание дневника
  (push, только mobile), резервная копия (экспорт/импорт/синхронизация).

Особенности платформ:
- Web: нет камеры штрихкодов и push; карта-заглушка; хранилище localStorage.
- Native: камера, геолокация, push, SQLite, генерация и шаринг PDF.

Источник требований: документ functional-requirements.md с идентификаторами вида FR-AUTH-01,
FR-DIARY-05 и т.д. Каждый тест-кейс должен ссылаться на соответствующий FR (если известен).

# Задание
Сгенерируй тест-кейсы для следующей области:
- Область (scope): {{SCOPE}}
- Платформа(ы): {{PLATFORM}}
- Требования (FR): {{FR_IDS}}
- Глубина покрытия: {{DEPTH}}
- Формат вывода: {{FORMAT}}

# Требования к тест-кейсам
1. Покрой типы проверок:
   - позитивные (happy path);
   - негативные (ошибки валидации, пустой/некорректный ввод);
   - граничные значения (например пароль 6 символов, телефон 10–15 цифр, шкала симптомов 0 и 10,
     период отчёта 7/14/30, история сканов = 5);
   - состояния отсутствия данных (нет профиля, пустой дневник, нет сети);
   - платформо-зависимое поведение (web vs native: камера, push, карта, хранилище);
   - переключение профиля и изоляция данных между профилями;
   - наличие обязательного disclaimer на медицинских экранах;
   - офлайн-поведение и деградация при отсутствии сети (Open-Meteo, Open Food Facts, sync).
2. Каждый тест-кейс должен быть атомарным, воспроизводимым и независимым.
3. Шаги — конкретные и проверяемые; ожидаемый результат — однозначный.
4. Не выдумывай функции, отсутствующие в контексте. Раздел «Ограничения текущей реализации»
   (push о пыльце, OCR, marketplace, PIN/биометрия, восстановление пароля и т.п.) считается
   нереализованным — для него создавай только тест-кейсы вида «функция недоступна», если это уместно.

# Поля каждого тест-кейса
- ID: TC-<МОДУЛЬ>-<номер> (например TC-DIARY-001)
- Заголовок: краткое название проверки
- Связанные FR: список идентификаторов (или «—»)
- Приоритет: P1 (критичный) / P2 (важный) / P3 (второстепенный)
- Тип: позитивный / негативный / граничный / платформо-зависимый
- Платформа: iOS / Android / Web / все
- Предусловия: состояние системы перед началом
- Шаги: пронумерованный список действий
- Ожидаемый результат: проверяемый итог
- Тестовые данные: при необходимости

# Формат вывода
- Если {{FORMAT}} = Markdown-таблица: одна таблица со столбцами из полей выше (шаги — нумерованным списком в ячейке).
- Если {{FORMAT}} = Gherkin: блоки Feature/Scenario с Given/When/Then, ID и FR в комментариях.
- Если {{FORMAT}} = JSON: массив объектов с ключами, соответствующими полям выше.

# Структура ответа
1. Краткое резюме покрытия (сколько кейсов, по каким модулям, распределение по приоритетам).
2. Тест-кейсы в выбранном формате, сгруппированные по модулям.
3. Список пробелов/допущений и вопросов, если требований недостаточно.

Весь вывод — на русском языке.
````

## Мини-промт (быстрый вариант)

````text
Ты — QA-инженер AllerGuide (Expo/React Native, RU-интерфейс, offline-first).
Сгенерируй тест-кейсы для: {{SCOPE}} на платформе {{PLATFORM}}.
Для каждого кейса укажи: ID (TC-<МОДУЛЬ>-<номер>), заголовок, связанный FR, приоритет (P1–P3),
тип (позитивный/негативный/граничный/платформо-зависимый), предусловия, шаги, ожидаемый результат.
Покрой happy path, негативные, граничные значения, состояния без данных и офлайн, web-vs-native различия,
переключение профиля и наличие disclaimer на медицинских экранах.
Не выдумывай нереализованные функции. Вывод — Markdown-таблица на русском.
````
